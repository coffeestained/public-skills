# C4 in five minutes

C4 is a way to draw software architecture as a set of zoomable maps. Each map is one level of detail, and each level uses one small set of building blocks. The notation is up to you. The discipline is not.

## The building blocks

- **Person**: a human user, role or persona.
- **Software system**: the biggest unit. Something that delivers value to its users and that one team owns end to end. Your product is one. Stripe is another.
- **Container**: something that has to be running for the system to work. An app, a service, a database, a queue, a bucket, a browser SPA, a mobile app, a serverless function. Not a Docker container, not a library.
- **Component**: a group of related code behind an interface, living inside one container. Controllers, services, repositories, modules. Not separately deployable.
- **Code**: classes, functions, tables. Usually left to the IDE.

A system holds containers. A container holds components. Components are made of code. People use systems.

## The four levels

Each diagram is described the same way: what is in scope, what the main boxes are, what supporting boxes are allowed, and who it is for.

| Level | Scope | Primary elements | Supporting elements | Audience |
| --- | --- | --- | --- | --- |
| 1. System context | One software system | That system | People and external systems directly connected to it | Everyone |
| 2. Container | Inside that system | Its containers | Connected people and external systems | Technical people, including ops |
| 3. Component | One container | Its components | Other containers, people and systems they touch | Developers and architects |
| 4. Code | One component | Classes, functions, tables | None | Developers, usually on demand |

Context and container diagrams are worth keeping for every system. Component diagrams only where they earn their place. Code diagrams almost never, by hand.

## Relationships

A line means "A depends on B" or "data flows from A to B", in one direction. Label it with the intent in plain words. Between containers, add the technology or protocol too (JSON/HTTPS, gRPC, SQS, JDBC).

Queues and topics are containers, since they store data. Draw producers pointing at the queue and the queue pointing at consumers. If that is too noisy, drop the queue box and write "via queue X" on the arrow.

## Notation rules

The model does not prescribe shapes or colours, only that the diagram can be understood on its own:

- Title: the diagram type and its scope, e.g. "Container diagram: Pulse".
- A key or legend that explains every shape, colour, border and line style.
- Every element shows its name, its type (Person, Software System, Container, Component), its technology where it has one, and a one-line description of what it is responsible for.
- Every line is labelled, points one way, and names its technology at the container level and below.
- Draw the boundary of the thing in scope so inside and outside are obvious.
- Use colours consistently across all diagrams, and keep them readable in black and white.

## Why bother

Diagrams at consistent levels of abstraction speed up onboarding, design reviews, risk-storming and threat modelling. Vague boxes labelled "business logic" do none of that.
